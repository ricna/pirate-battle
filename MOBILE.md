# Mobile display

Phones use a player-following camera instead of shrinking the complete arena. At 844×390 the canvas shows approximately one quarter of the authored map area, so the 2048×1152 map is explored by sailing. The camera clamps to each shore. Desktop keeps the reference overview. Rendering never changes world coordinates, speed, collision, spawn positions or ranking identity.

`src/game/configuration/CameraConfig.ts` owns display-only tuning: compact mode at width ≤1024 or height ≤600 CSS pixels, a 0.25 visible-area fraction and a minimum scale of 0.75 CSS pixels per world pixel. The minimum keeps the 113-pixel player hull at least 84.75 CSS pixels long on small landscape screens. Narrower phones may show less than a quarter of the map to preserve readability. `WorldCamera` owns the transform; `MapRenderer` applies it and continues to render the authored cached surface. The camera is observable through the existing read-only test instrumentation.

The compact HUD uses a grid for health, score, time and pause. Movement/fire buttons are 60.8 CSS pixels; pause and menu controls are at least 44 pixels high. CSS reads the safe-area insets through `--safe-top`, `--safe-right`, `--safe-bottom` and `--safe-left`, which the rotated layout remaps to the device edges they face.

Compact screens keep fixed control sizes in every orientation and shrink each board to its content (D22): extra width becomes space around the board, never wider buttons. Play/Options-style buttons are 220 × 48 px (202 × 44 px on the Captain's Log, the tallest board), secondary buttons 150 × 44 px, controls stay at least 4 px apart and labels keep 22 px from the rounded ends of the button art. The tokens live on `:root` in `src/ui/App.css`. Main Menu places the title beside Play and Options on short landscape screens, with Ranking, Match History, How To Play and Quit in a 2 × 2 grid. Options places Game and Audio side by side in landscape, with the closing actions under the shorter Game column; on the narrowest phones (≤ 640 px wide) its sliders narrow to 56 px. Captain's Log keeps a compact table, How To Play offers Overview, Controls and Enemies as separate topics, and the Battle result uses a centered overview beside compact statistic cards. These screens and paused Options fit the supported phone viewports without page, screen, table or dialog scrolling. Short landscape screens keep a 48 px bottom strip for the collapsed demo network panel; at 360 px tall or less the panel appears only on the Main Menu. The original supplied art remains the source for panels and controls.

## Rotated landscape layout

The game is landscape on every touch device. `#root` is the layout container of every screen (`container: app / size` in `src/ui/App.css`): screens size themselves with container units (`cqw`, `cqh`) and `@container app` queries, never viewport units or media queries. When a coarse-pointer device reports portrait (`(orientation: portrait) and (pointer: coarse)`), `#root` takes the swapped size and turns a quarter clockwise, so its top meets the device's right edge and the player turns the device to the left to read it. When the browser then reports landscape, the rotation disappears and the layout keeps the same size, so combat continues without a pause or a rotate prompt. This also covers phones with rotation lock held sideways.

Modal dialogs render in the browser's top layer, outside `#root`'s transform, so each `dialog:modal` turns about the screen centre in the rotated layout and measures `#root` through container units. Pointer movements arrive in screen coordinates: `LayoutAxes` (`src/ui/hud/LayoutAxes.ts`) converts the Forward drag into the layout's own axes, so steering follows the direction the player sees. `GameSession` pauses only when the arena itself is portrait (a narrow desktop window), observed through its ResizeObserver.

Native browser surfaces outside the page, such as the system picker of the demo panel's `<select>`, are not rotated. Touch scrolling and pickers on rotated pages still need physical-device inspection.

## Full screen and Quit

Full screen is required (D21). Browsers grant it only during a user gesture, so `FullscreenDisplay` (`src/infrastructure/browser/FullscreenDisplay.ts`) listens for document `pointerup` and plain `keydown` gestures and requests full screen for the document root at the first one, keeping menus, dialogs and battles in one session. After a browser exit (holding Esc, Android back) the next gesture returns to it, without pausing a battle. Escape and keys pressed with a modifier never count as gestures, and `navigator.userActivation` confirms that a gesture is active before the request. No screen shows a full-screen button.

**Alt+Enter** (including the numeric keypad Enter) is the computer player's explicit choice: it leaves full screen for a window until the next Alt+Enter, which enters again. A running battle pauses first, and Resume stays explicit. Held-key repeats never toggle twice or activate the focused button. `DisplayConfig` authors the bindings, the exit key, the single key requested through Keyboard Lock (Escape) and the locked orientation (landscape).

After entering, the display requests `navigator.keyboard.lock(['Escape'])` where Keyboard Lock exists, so a short Esc reaches the game's pause and native dialogs, and `screen.orientation.lock('landscape')` where the browser allows it (mainly Android in full screen); the rotated layout covers the others. Both captures are optional, released on exit and teardown, and released again after a late grant to an exited screen. The browser's long-Esc escape hatch remains. [Chrome's Keyboard Lock behavior](https://developer.chrome.com/blog/better-full-screen-mode), [Screen Orientation lock](https://developer.mozilla.org/en-US/docs/Web/API/ScreenOrientation/lock).

**Quit**, in the Main Menu's bottom row on every platform, leaves full screen and then calls `window.close()`. Browsers only let a page close a tab that a script opened or that has no other history; when the tab stays open, the Quit dialog asks the player to close it and offers Return to the game, which re-enters full screen from that tap.

`DisplayGuidance` (`src/ui/components/DisplayGuidance.tsx`), rendered by `ServicesProvider`, shows the display's notices: a browser without page full screen (iPhone Safari, answering Alt+Enter with the Add to Home Screen route), a refused request (reported once, with Try again; gestures stop retrying) and a tab the browser kept open. `ServicesProvider` owns the display's document listeners and releases them and both captures at application teardown. The manifest asks an installed web app for full-screen landscape display; Safari ignores both requests. [Fullscreen API behavior and user activation](https://developer.mozilla.org/en-US/docs/Web/API/Element/requestFullscreen).

## Verification

`tests/mobile.spec.ts` covers four landscape sizes (568×320, 667×375, 844×390, 932×430) and two portrait sizes (320×568, 390×844), which show the rotated landscape layout: readable controls in the layout's own axes, no HUD overlap, menu/table containment, turning the device both ways during a battle without a pause, real sailing, camera movement/pause, all four camera bounds and the desktop overview. Display cases cover required full screen at the first gesture and after a browser exit, Escape never entering it, Alt+Enter's window choice and battle pause, unsupported and refused full screen, Keyboard Lock (native, missing, denied and late), the lazy engine, Quit closing a script-opened tab, Quit leaving full screen before a refused close, and Forward drag steering in the rotated layout. Run `npm run test:e2e -- --project=mobile-layout`; its captures go to the Git-ignored `test-results/evidence/mobile-layout`. A delivery run (`npm run test:deliver`) writes them to `reports/mobile-layout`, beside the isolated verification reports kept there.

The screen-fit cases check Main Menu, Options, Captain's Log, all three help topics, Pause/Options and Battle result at 568×320, 844×390 and 320×568. They assert that every board and visible button remains inside the viewport, that visible controls keep at least 4 px from each other and from the demo panel, and that the document, the screen, the records table and the pause dialog do not scroll. This is browser emulation evidence; physical devices still need inspection.

The final focused run passed 16/16 scenarios, including production smoke and the three cases rechecked after the full 120/123 run. The full run's two startup timing failures and preceding result-baseline mismatch remain recorded; it is not relabeled 123/123. Linux reference captures passed 2/2 in the CI container. See [verification evidence](reports/mobile-layout/VERIFICATION.md). Physical devices remain unverified.

Required full screen, Quit, the rotated layout (D21) and compact fixed-size controls (D22) were verified on 14 October 2026 on that change alone, in an isolated worktree without concurrent uncommitted work: typecheck, lint, format check and production build passed, and the complete Playwright suite passed 147/147 (`mobile-layout`, `core`, `rendering` and `production-smoke` 55; `desktop` 46; `mobile-landscape` 46). The Windows menu, arena and result baselines were regenerated for this intentional visual change; the Linux baselines (`npm run test:docker`) were not. No physical phone, tablet, iOS or Android browser was tested.
